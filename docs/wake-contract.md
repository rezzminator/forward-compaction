# What the wake must carry

- The wake exists to carry content: a woken party continues with everything it needs, and no size budget outranks a rule in this section.
- The frontier is two texts, `objective` and `next`, and six numbered lists, `orders`, `decisions`, `done`, `remaining`, `blocked` and `findings`, each changed by `{add, remove, edit}` by item number; whatever a call leaves out stays, and an item's number never shifts and is never reused. The wake renders it from the lists, never from text the model wrote whole. In a wake an item of any list ends with ` [N rounds unchanged]` once N compactions were installed since its add or last edit, none before its first, and one sentence (`unchangedNote`) says what the tag means; the plugin counts it, a tag the model sends back at an add or edit text's end is stripped, as is a `[n]` number it types before an item's text (an edit's own number only), and `objective`, `next` and storage entries carry none.
- A call is never refused: a malformed entry, a field the tool does not take or an old-style field (`standing_orders` taken as `orders.add`; `lifted`, `keep_skills`, `drop_files`, `drop_skills`, a load file's `later`) is answered by a note. A list, `storage` or `load_files` value sent as the text of its JSON is read as that JSON, broken JSON first repaired (`repairJson`, a list's operations named bare or by leaked tool-call tags read as operations) and arguments written after a value closed early taken out as their own, one note per field; a text that is no JSON stays one added item, one that is only an operation's name adds nothing and is answered by a note.
- The frontier has no length cap: it is stored whole and installed whole but for `done`'s older items, never trimmed or summarized for its size; past `FORWARD_COMPACTION_FRONTIER_WARN_CHARS` a frontier with no list item is asked for a shorter `objective` and `next`, one whose lists hold items is asked nothing (`sizeLines`), and nothing is cut.
- Only `done` splits, at each rendering (`doneSplit`): a wake shows its newest items while their texts fit `FORWARD_COMPACTION_DONE_MAX_CHARS`, the newest always, under one line naming `done-earlier.md`, which holds each older item whole as `[n] text`; the store keeps every item, so `edit` and `remove` reach an earlier one by number. It keeps each live item it held until a later compaction ask's transcript holds the last wake rendered, showing it (`doneReached`). A wake splits only while the file is known to hold all that (`doneWake`), else shows the whole list, as when a failed write, its own or its record's ahead of it, leaves it unwritten, which the call's result does not name.
- A frontier without `objective` or `next` is stored, waits and installs as it is, its result and its wake naming what it lacks, unless a later call sends it first.
- `decisions` carries every ruling the user gave on how something gets done, in the user's words, each with its undo when one exists; a rule that binds the rest of the work is a standing order.
- A skill or command the party loaded is carried whole under `## Skills in force, as loaded` only when pinned (its frontmatter's `forward-compaction-keep: true`, or `FORWARD_COMPACTION_KEEP_SKILLS` naming it, `*` every one); every other one is listed under `## Skills not carried` by name, source, path and frontmatter description, with `SKILLS_LISTED_NOTE`. The carried ones fit Claude Code's own post-compaction limits: newest loaded first, each cut past `SKILL_MAX_CHARS` to its head and Claude Code's own truncation marker, all together within `SKILLS_MAX_CHARS`, and one that does not fit what is left named as not carried with the call that loads it again.
- The user's ten newest typed messages (`PROMPTS_KEPT`, main) and every answer they gave to the model's AskUserQuestion, however old, or the brief (sub-agent), are carried whole into every wake, whatever their size; the heading counts the answers and the older typed messages left out.
- Every wake of a sub-agent, frontier or mechanical, reads in the documents its brief names (`briefFiles` picks, `readBriefFiles` reads, `brief-files.ts`): each path the brief names, absolute or under `~` once the home directory is known, with a `BRIEF_FILE_EXTENSIONS` extension, that one of the party's own calls opened (a Read, or a shell command naming it as a whole path), that the party did not write or edit, and that its frontier does not list in `load_files`. They are read at install in the brief's order, together within `BRIEF_FILES_MAX_CHARS`: the one that crosses it is cut at its last line that fits and names where to Read on; one with no room, unreadable, empty or binary is named under `## Files not carried`. They stand under `BRIEF_FILES_HEADING` with `BRIEF_FILES_NOTE`: they are part of the brief, and where the frontier words one of their rules differently, the document's words hold.
- A standing order is the user's order that binds the rest of the work (a prohibition, a limit, a rule), in the user's words in an `orders` item, which several rules may share; it survives every wake, the mechanical one included, until a call removes its item by number in `orders.remove` or edits the item down to its other rules, with no proof asked, never keeping it as a lifted note.
- The wake renders the standing orders above the frontier, marked binding, each as `[n] text` with its rounds-unchanged tag.
- Only what the model can find again is fitted to a budget: `done`'s older items, the kept tail, the notifications and delivered messages, sibling results, the shell commands run (verbatim, each with its description), and the files and agents lists. The task list is carried whole; each `load_files` file carries up to `LOAD_FILE_MAX_LINES` lines, a longer one naming where to Read the rest, with no room and no count cap, never refused for size. Each one left out is named as not carried, never silently gone.
- Plan mode and the plan file, as Claude Code's plan-mode attachments name them for the party, are carried into every wake, the plan file read whole at install; the plugin API exposes no active goal, so the wake carries none.
- A mechanical wake re-reads the `RECENT_FILES_KEPT` newest files the party touched from disk, less a document its brief names, each within `LOAD_FILE_MAX_LINES`, as Claude Code's own compaction does because it fires uninvited; a frontier wake reads in only its `load_files` and its brief's documents. A call that sends `load_files` replaces the earlier call's; one that leaves it out keeps them.
- A `storage` entry is a markdown file the party keeps for a later step and reads or edits itself; every wake of the party, the mechanical one included, lists each entry under `## Storage` by name and description beside the folder's absolute path, never its content.
