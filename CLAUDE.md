# forward-compaction

A Claude Code function-hooks plugin: the model writes its own frontier through
one tool, and the plugin installs it at Claude Code's compaction. `docs/spec.md`
is the behavioural spec.

## Function

Claude Code's own compaction has a separate call summarize the transcript. Here the working model, main chat or sub-agent, writes its own frontier at a milestone it picks, sending only the changes to the numbered lists the plugin holds on disk, and the plugin installs it with the user's words and standing orders verbatim and the facts it recorded as they happened, so the party continues with no decision, order or open thread lost.

## Spine

`model works -> plugin nudges as its context grows -> from a notice on, model picks its milestone and calls forward_compaction -> frontier stored -> Claude Code's next compaction ask -> plugin installs the frontier -> model wakes`

- The model chooses when to compact, from a notice on: the plugin only nudges, first at a party's nudge-start (absolute), then one per nudge-every; after a wake, a nudge-start above its floor (`roomAbove`, held two nudge-every below the ceiling). A set nudge-room moves the first nudge, after a wake too, that far above the floor (`nudgeStart`). Floor (`floor.json`): a party's first reading ever; after an install, the larger of its first two readings, as only the second request carries what Claude Code sends back (`Held.settling` between them); any reading below a settled floor, which restarts the nudges and the finish notice.
- A `forward_compaction` call always stores, and compacts (`callCompacts`, `Parties.compacts`) only once the party's context has reached a notice point since its last install: main's finish notice point (`finishReached`) or a nudge point, after a wake its room (`roomAbove`) above the wake's floor. Below it a call only updates the held frontier: nothing compacts, and nudges and the finish notice still go out when due. Not judged, so its call compacts: a party with no marks (its window unknown), an ignored model, a party with no reading yet; a woken party with no reading since its wake does not compact.
- Each nudge names the context's size and asks for a frontier in the words of its count since the party's last install (`nudgeBody`), each firmer than the one before, the first three timing the call between two steps, the last before the ceiling saying the plugin compacts next; it names no max context and no ceiling, and prints no list: a party holding a frontier is asked for its changes by item number, one holding none for a first frontier.
- Main also compacts when its whole work is finished, before the final report, so the user's reply meets a small context: its first three nudges carry that rule (`FINISH_RULE`), and at or past `FORWARD_COMPACTION_MAIN_FINISH_START` and one nudge-every above its floor (`finishReached`), with no nudge sent, it reads the finish notice once per install (`finishDue`); a sub-agent, whose context ends with its report, is never asked, its first three nudges saying when it may skip (`SKIP_RULES`).
- The plugin holds Claude Code's compaction. `CLAUDE_CODE_AUTO_COMPACT_WINDOW=100000` exists only so Claude Code asks early, about every request from about 63k; it is never the compaction point.
- Each ask is skipped until a stored call compacts, its frontier complete or not, and that ask installs it; or until the party reaches its ceiling, and it gets the mechanical wake: recorded facts and the frontier the plugin holds, as it stands. Main also installs a stored call that compacts at its own turn end, through `$.session.compact()`.
- The exceptions to "the model chooses" are only these:
  - the ceiling: the mechanical wake, or Claude Code's own summary under `FORWARD_COMPACTION_CEILING_NATIVE`;
  - a request too long (an ask following a held ask in the same turn that no request completed): the mechanical wake at once, below the ceiling;
  - an ignored model (`FORWARD_COMPACTION_IGNORE_MODELS`, Haiku by default): no nudges, its asks held to its ceiling and then compacted mechanically, never at Claude Code's early ask; its `forward_compaction` call is stored like any other's;
  - an error, which never holds a compaction: the party gets the mechanical wake, and if that fails too, Claude Code's own summary runs; every failure is logged with context;
  - the user's own `/compact`: Claude Code's own summary, and the stored frontier is dropped, said only for a call that compacts;
  - Claude Code's own fork, a party not ours: its ask passes.
- A party with no reading yet is held until its next reading; one whose window is unknown never reaches its ceiling. A precompute ask is always skipped.
- Parties: the main chat and each sub-agent by its agentId, each with its own state, max context, ceiling and nudge levels, set by `FORWARD_COMPACTION_MAIN_{MAX_CONTEXT|CEILING|NUDGE_ROOM|NUDGE_START|NUDGE_EVERY}` and `FORWARD_COMPACTION_SUBAGENT_{…}`.
- Each party's frontier and storage live in `$HOME/.local/state/forward-compaction/{project}/{session id}/` (a sub-agent's under `agents/{agent id}/`): `orders.json`, `data/{objective|decisions|done|remaining|next|blocked|findings}.json`, `storage.json`, `storage/{name}.md`, `rounds.json` (the party's count of installed compactions; each list item's `round` is that count at its add or last edit, absent 0), `floor.json` (`{floor, settled}`; an unsettled one is not loaded, the party's next reading being its floor), and the `history` folder, where the plugin appends every value that leaves and the model never reads. The plugin alone writes them: a call's changes when it makes them, `rounds.json` right after each install of a party holding a list item, `floor.json` at each new floor; no file holds a date or time, nothing is ever deleted, and a restarted or resumed chat keeps every number.
- The install: everything `## What the wake must carry` holds, the frontier, the recorded facts (the messages delivered to the party, agents, shells, the files touched, the shell commands run, the task list, plan mode and the plan file), the documents a sub-agent's brief names, the `load_files` (a mechanical wake: the party's newest files, re-read from disk), the storage entries, listed and never read, the newest messages after the call that fit, kept verbatim, and every delivery recorded after the call that those messages lack.
- A sub-agent's party lives across its runs: one waiting on its background children ends a turn and is resumed by each child's notification, so a turn end is never its finish.

## What the wake must carry

- The wake exists to carry content: a woken party continues with everything it needs, and no size budget outranks a rule in this section.
- The frontier is two texts, `objective` and `next`, and six numbered lists, `orders`, `decisions`, `done`, `remaining`, `blocked` and `findings`, each changed by `{add, remove, edit}` by item number; whatever a call leaves out stays, and an item's number never shifts and is never reused. The wake renders it from the lists, never from text the model wrote whole. In a wake an item of any list ends with ` [N rounds unchanged]` once N compactions were installed since its add or last edit, none before its first, and one sentence (`unchangedNote`) says what the tag means; the plugin counts it, a tag the model sends back at an add or edit text's end is stripped, as is a `[n]` number it types before an item's text (an edit's own number only), and `objective`, `next` and storage entries carry none.
- A call is never refused: a malformed entry, a field the tool does not take or an old-style field (`standing_orders` taken as `orders.add`; `lifted`, `keep_skills`, `drop_files`, `drop_skills`, a load file's `later`) is answered by a note. A list, `storage` or `load_files` value sent as the text of its JSON is read as that JSON, broken JSON first repaired (`repairJson`, a list's operations named bare or by leaked tool-call tags read as operations) and arguments written after a value closed early taken out as their own, one note per field; a text that is no JSON stays one added item, one that is only an operation's name adds nothing and is answered by a note.
- The frontier has no length cap: it is stored and installed whole, never trimmed or summarized for its size; past `FORWARD_COMPACTION_FRONTIER_WARN_CHARS` a frontier with no list item is asked for a shorter `objective` and `next`, one whose lists hold items is asked nothing (`sizeLines`), and nothing is cut.
- A frontier without `objective` or `next` is stored and installs as it is, its result and its wake naming what it lacks, unless a later call sends it first.
- `decisions` carries every ruling the user gave on how something gets done, in the user's words, each with its undo when one exists; a rule that binds the rest of the work is a standing order.
- A skill or command the party loaded is carried whole under `## Skills in force, as loaded` only when pinned (its frontmatter's `forward-compaction-keep: true`, or `FORWARD_COMPACTION_KEEP_SKILLS` naming it, `*` every one); every other one is listed under `## Skills not carried` by name, source, path and frontmatter description, with `SKILLS_LISTED_NOTE`. The carried ones fit Claude Code's own post-compaction limits: newest loaded first, each cut past `SKILL_MAX_CHARS` to its head and Claude Code's own truncation marker, all together within `SKILLS_MAX_CHARS`, and one that does not fit what is left named as not carried with the call that loads it again.
- The user's ten newest typed messages (`PROMPTS_KEPT`, main) and every answer they gave to the model's AskUserQuestion, however old, or the brief (sub-agent), are carried whole into every wake, whatever their size; the heading counts the answers and the older typed messages left out.
- Every wake of a sub-agent, frontier or mechanical, reads in the documents its brief names (`briefFiles` picks, `readBriefFiles` reads, `brief-files.ts`): each path the brief names, absolute or under `~` once the home directory is known, with a `BRIEF_FILE_EXTENSIONS` extension, that one of the party's own calls opened (a Read, or a shell command naming it as a whole path), that the party did not write or edit, and that its frontier does not list in `load_files`. They are read at install in the brief's order, together within `BRIEF_FILES_MAX_CHARS`: the one that crosses it is cut at its last line that fits and names where to Read on; one with no room, unreadable, empty or binary is named under `## Files not carried`. They stand under `BRIEF_FILES_HEADING` with `BRIEF_FILES_NOTE`: they are part of the brief, and where the frontier words one of their rules differently, the document's words hold.
- A standing order is the user's order that binds the rest of the work (a prohibition, a limit, a rule), in the user's words in an `orders` item, which several rules may share; it survives every wake, the mechanical one included, until a call removes its item by number in `orders.remove` or edits the item down to its other rules, with no proof asked, never keeping it as a lifted note.
- The wake renders the standing orders above the frontier, marked binding, each as `[n] text` with its rounds-unchanged tag.
- Only what the model can find again is fitted to a budget: the kept tail, the notifications and delivered messages, sibling results, the shell commands run (verbatim, each with its description), and the files and agents lists. The task list is carried whole; each `load_files` file carries up to `LOAD_FILE_MAX_LINES` lines, a longer one naming where to Read the rest, with no room and no count cap, never refused for size. Each one left out is named as not carried, never silently gone.
- Plan mode and the plan file, as Claude Code's plan-mode attachments name them for the party, are carried into every wake, the plan file read whole at install; the plugin API exposes no active goal, so the wake carries none.
- A mechanical wake re-reads the `RECENT_FILES_KEPT` newest files the party touched from disk, less a document its brief names, each within `LOAD_FILE_MAX_LINES`, as Claude Code's own compaction does because it fires uninvited; a frontier wake reads in only its `load_files` and its brief's documents. A call that sends `load_files` replaces the earlier call's; one that leaves it out keeps them.
- A `storage` entry is a markdown file the party keeps for a later step and reads or edits itself; every wake of the party, the mechanical one included, lists each entry under `## Storage` by name and description beside the folder's absolute path, never its content.

## A run, as expected

Each step names what an audit of the transcript and the plugin's log rows sees.

1. Below its first nudge level the party works undisturbed: each Claude Code ask logs `compact` with decision `skip`, why `waiting`, and nothing reaches the model but main's finish notice (step 2).
2. At each nudge level the model reads one nudge with a tool result, logged `nudge` with its level, its `notice` count and `last`; no level nudges twice, and no two nudges between installs read alike. Main at its finish notice point (`finishReached`) reads the finish notice once before its first nudge, logged `finish-notice`.
3. The model finishes its step, then calls `forward_compaction` with only its changes, removing what is finished, lifted or wrong and editing what changed: the result gives one line per change with its item numbers, an item that left (removed, or the text an edit replaced) shown by its first `LEFT_SHOWN_CHARS` characters, its whole text in the list's history file, a note per skipped entry, the frontier's size, then `Frontier stored`, or below the notice point `Frontier updated`, and a `stored` row records `compacts`, its `lists`, `frontier`, `storage` and `files`. A frontier without `objective` or `next` gets `, without {objective|next}: send it before it installs, or the wake names it missing`; its `stored` row, and the `compact` row that installs it, carry `incomplete`.
4. The next ask installs a stored call that compacts (main also at its own turn end; after one that does not, asks stay as in step 1): `compact` with decision `install`, why `stored`, then `landed` with `before` above `after` and the cache `read` and `written` of the first request after it; the transcript holds one compact boundary per install.
5. The wake is the facts message (`[forward-compaction: facts]`), the frontier message (`[forward-compaction: frontier]`, the frontier rendered from its lists), then the kept tail. A sub-agent's wake opens with its start (`keptStart`): the user messages its transcript opens with (its brief, with what Claude Code attached) handed back untouched by handle, then the fixed assistant line `START_END`, so each later compaction reads that prefix from the prompt cache; its facts head points to the brief above in place of `## Your brief`, and the `wake` debug row's `start` counts the messages above the facts and its `briefFiles` names the documents picked. The facts run in this order, an empty section left out or saying why it is empty: standing orders; messages arrived after the frontier; plan mode and plan file; the brief and the documents it names (sub-agent) or the user's messages (main); notifications or delivered messages; results of the calls beside the frontier; skills in force and skills not carried; files touched; shell commands run; tasks; agents; background shells and crons; the `load_files` carried; the storage; the files not carried; on a mechanical wake, the files being worked on. Outside Claude Code's expanded view (ctrl+o, `--verbose`, an export) `wakeRow` folds these hook-built rows (origin `unclassified`, or `coordinator` in a sub-agent's view; the user's typing never folds): the facts message draws nothing, the message after it (the frontier, or a mechanical wake's no-frontier message) one dim line naming ctrl+o; the stored messages the model reads stay whole.
6. Every fact is true of the woken party: nothing another party read, loaded, ran or started appears as its own, and a fact the plugin cannot tie to a party says so.
7. After the wake the party continues from its `next`, obeys every standing order and ruling, redoes nothing its `done` lists, and finishes its task correctly.
8. The run writes no `errors.jsonl` or `warnings.jsonl` row for the party, and every number in a nudge, receipt or wake has its API source (§ Rules).

## Layout

- `plugins/forward-compaction/`: everything that installs, and nothing else — the directory scans only this folder, so dev files never go in it.
- `plugins/forward-compaction/hooks/forward-compaction.ts`: the adapter, the only file that touches `$`.
- `plugins/forward-compaction/contract.d.ts`: the session state the host keeps for the plugin (`$.state`, by party: its newest prompts, its loaded skills, its ignore judgement, and the standing orders an earlier build kept there, read once to seed its numbered orders); `plugin.json` names it in `types`.
- `plugins/forward-compaction/src/`: every decision, pure and unit-tested, the per-session files reached only through the `Fs` the adapter hands in (`disk.ts`, `storage.ts`); `tests/` holds one vitest file per concern.
- `types/claude-code.d.ts`: the plugin API (from `/plugin-types`), the truth for every hook's shape; grep it before using an event.
- `plugins/forward-compaction/.claude-plugin/`: `plugin.json` (manifest, no `userConfig`) and `icon.svg`; the plugin installs as `forward-compaction@professor`.

## Commands

`npm test`, `npm run typecheck` and `npm run validate:plugin` all pass before a commit. `make release-check` runs every check `ci.yml` runs on a `develop → main` pull request, the same make targets (`check`, `release`) under Node 22. A live check loads the checkout with `--plugin-dir plugins/forward-compaction`: the installed copy is disabled in the same `--settings`.

Refresh the installed copy with `claude plugin marketplace update` as written, never under a `CLAUDE_CONFIG_DIR` override pointing at `~/.claude`: `claude` then writes `.claude.json` and `backups/` into the shared store.

## Rules

- forward-compaction NEVER blocks, refuses, delays or holds back any operation of any agent or of the main chat. Every tool call runs. The plugin only nudges, and compacts mechanically at a party's ceiling.
- Every number the plugin decides on or reports comes from Claude Code's plugin API, as far as it reaches: `$.session.usage()` (window, auto-compact threshold), `turn.step` usage (each party's reading), `session.compact`'s `tokensBefore`/`tokensAfter`, `$.agent.list()`, `$.session.messages()`; a sub-agent's window, which that API reports for the main chat's model alone, comes from the Anthropic Models API (`max_input_tokens`), asked through `$.session.authorize()` and `$.http.fetch`.
- No guessed, estimated or invented number: no character-count token estimates, no hard-coded model-window tables; the `[1m]` context marker in the model id a step reports is the API's own literal, not a model-name table.
- Where the API gives nothing, a value a user tunes (a max context, ceiling or nudge level) is a named option with its default; a sub-agent's max context, unset, is its model's window from the first source that knows it (that marker, main's reported window when its model id is the one main last named, the Models API), and while none does, the named fallback `DEFAULT_SUBAGENT_MAX_CONTEXT`, its `window` decision row saying the window is unknown and why; a design budget (the wake's section shares, the skills' character limits, a format cap such as `WHY_MAX_CHARS` or `LOAD_FILE_MAX_LINES`) is a named constant whose one-line comment says why, and is never reported as a measured size.
- A number with no source is unknown and is said as unknown.
- Every step writes a debug row (`debug.jsonl`), so any decision traces back to its inputs; a transcript draw is no step and writes none.
- A new behaviour lands in `plugins/forward-compaction/src/` as a pure function with a test watched failing first; the adapter only wires it.
- A bad option is logged by its variable and falls back to its default.
- Every option is read from a variable `FORWARD_COMPACTION_{OPTION}`, upper snake, and nowhere else: the plugin declares no `userConfig`, and a non-empty options object handed to `register` is named in one warning and not applied. Flags `1|0|true|false`, any case; sizes, dirs and log file the option's grammar; unset, empty or blank is absent; a bad value is named by its variable and the default applies.
- A new option adds its variable to `OPTION_ENV` (`plugins/forward-compaction/src/options.ts`), a literal `readOptionVar` line to the adapter and its README options-table entry; `tests/register.test.ts` holds the literals to `OPTION_ENV`.
- A version bump moves `plugins/forward-compaction/.claude-plugin/plugin.json`, `package.json` (and its lockfile) and the README badge together; installed copies update only on a new version.
- The README tests badge states the count of tests `npm test` passes; `npm run release:check` runs the suite and fails when they differ, so the badge is set last, after the final test is added.
- Defaults live in two places only, and agree: `plugins/forward-compaction/src/options.ts` (`DEFAULT_*`, `MARKED_SUBAGENT_MAX_CONTEXT`) and the README options table; this file names an option, never its default number.
- The README benchmark reports measured runs only; a figure the code has changed since is labelled not re-measured.
- Public repo: no machine-absolute paths, personal data or private project names in a tracked file.
- `$` is passed only to functions declared at the top level of the hooks file and always spelled `$.noun.event(...)`: Claude Code checks this statically and otherwise loads the module with zero hooks. `npm run validate:plugin` catches it.

## Branches and releases

- `develop` is the default branch: every change lands there, by a commit or a pull request, and no CI runs on a push. `.github/workflows/ci.yml` runs on the `develop → main` pull request only, and `.github/workflows/publish.yml` on its merge. `develop` is protected by the ruleset `develop keeps its history`: never force-push or delete it.
- `main` is release-only (ruleset `main is release-only`). It moves only by merging the `develop → main` pull request, with a merge commit and never a squash, so both branches share one history, and only after its `ci` check passes: never a direct push, never an admin override. Professor's marketplace installs the plugin from `main` (`git-subdir`, `ref: main`), so users only ever get a released version.
- A release, in order:
  1. On `develop`: bump the version in all four places, and move `## [Unreleased]` in `CHANGELOG.md` to `## [X.Y.Z] — date`. Every merge into `main` publishes, so a pre-release suffix (`-dev.N`, `-alpha`) becomes the real release version here.
  2. `make release-check` passes, after `git fetch origin main`.
  3. Open the `develop → main` pull request. Its `ci.yml` runs the same make targets, `check` on Linux and macOS and `release`, and its `ci` job passes only when every one succeeded; `release` requires the version to have moved past `main`'s and the CHANGELOG section to yield notes.
  4. Merge once `ci` is green. The merge is the release: `publish.yml`'s `publish` job tags the merge commit `forward-compaction--vX.Y.Z` and publishes the GitHub release from the CHANGELOG section. No tag is pushed by hand.
- Semantic versioning: a fix is a patch; a new option or behaviour is a minor; a renamed or removed option is a major, and its CHANGELOG entry says how to migrate.
- Publishing: code is pushed, and a release is cut, only when the owner asks.
- Git writes go through this repo's gitter, `.claude/agents/gitter.md`.
